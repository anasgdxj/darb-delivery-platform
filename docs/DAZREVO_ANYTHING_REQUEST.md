# DAZREVO — «اطلب أي شيء» (Any Request)

الحالة: ميزة معتمدة من مالك المنتج — مرحلة التصميم الهندسي  
الفرع: `feat/dazrevo-anything-request`  
Issue: #133

## 1. القرار المعماري

الميزة ليست إعادة تسمية لـ `PEER_DELIVERY`. هي نوع مهمة شراء وتوصيل مستقل، وتستفيد من البنية الحالية لعروض السائقين والتتبع والإشعارات، مع فصل تكلفة المشتريات عن أجرة التوصيل.

المكونات الحالية التي يعاد استخدامها:
- `AiOrderDraft` لتحليل وصف العميل ومقترحات المنتجات عند الحاجة.
- `Order` و`DeliveryOffer` ودورة `PEER_DELIVERY` لاكتشاف السائقين وتقديم أجرة التوصيل.
- عناوين العميل والخرائط والإشعارات والتتبع الحالي.
- نظام التصميم `DESIGN_SYSTEM.md` والترجمة الحالية AR/EN/TR.

لا يتم تعديل تدفق `VENDOR_ORDER` ولا كسر طلبات `PEER_DELIVERY` الحالية.

## 2. تجربة العميل

1. بطاقة مستقلة في الصفحة الرئيسية بعنوان «اطلب أي شيء».
2. إدخال وصف الغرض والكمية والمواصفات، مع صورة اختيارية في مرحلة دعم الرفع.
3. إدخال اسم المتجر/السوق وعنوانه أو اختيار «اقترح مكاناً مناسباً».
4. اختيار عنوان التسليم المحفوظ وتأكيد النقطة الجغرافية.
5. ميزانية شراء اختيارية بعملة المدينة. الميزانية ليست سعراً نهائياً ولا تفويضاً بالشراء.
6. مراجعة نهائية واضحة قبل إرسال المهمة.
7. مقارنة عروض أجرة التوصيل من السائقين واختيار سائق.
8. استقبال عرض شراء منفصل يتضمن قيمة المنتجات والعملة وتفاصيل الإيصال/البدائل.
9. موافقة صريحة على قيمة الشراء أو رفضها. لا شراء ولا انتقال إلى مرحلة الاستلام دون الموافقة.
10. متابعة السائق حتى التسليم، مع فصل بند «المشتريات» عن «أجرة التوصيل» في الفاتورة.

## 3. تجربة السائق

- تمييز المهمة في قائمة الطلبات المتاحة بوسم شراء وتوصيل.
- عرض وصف الغرض والمتجر والميزانية وموقع التسليم الضروري فقط.
- تقديم أجرة التوصيل عبر آلية `DeliveryOffer` الحالية.
- بعد اختيار السائق، يرسل تكلفة الشراء الفعلية، تفاصيل الأصناف/البدائل وملاحظة الإيصال.
- لا يستطيع السائق بدء الشراء أو تسجيل الاستلام قبل موافقة العميل على المبلغ الحالي.
- أي تعديل على المبلغ بعد الموافقة يلغي الموافقة السابقة ويعيد الطلب إلى انتظار موافقة جديدة.
- بعد الشراء يسجل إثبات الشراء، ثم يستكمل حالات التوصيل والتتبع الموجودة.

## 4. نموذج البيانات المقترح

التغيير يجب أن يكون متوافقاً مع البيانات القديمة:
- إضافة نوع طلب جديد واضح مثل `SHOPPING_DELIVERY` بدلاً من تخزينه كنص داخل `notes`.
- حقول طلب شراء: وصف الغرض، اسم/عنوان المتجر، ميزانية العميل الاختيارية.
- سجل منفصل `ShoppingPurchaseQuote` مرتبط بالطلب: المبلغ، العملة، تفاصيل الأصناف، ملاحظة/مرجع الإيصال، الحالة، منشئ العرض، وقت الإرسال، وقت موافقة العميل.
- حالات العرض: `PENDING_CUSTOMER_APPROVAL`, `APPROVED`, `REJECTED`, `SUPERSEDED`.
- سجل تدقيق أو تاريخ حالات لا يمكن تغييره بصمت.

يجب مراجعة علاقات Prisma الحالية وسياسة ترحيل قاعدة البيانات قبل تثبيت أسماء الحقول النهائية. لا تُعدّل بيانات الإنتاج مباشرة.

## 5. واجهات API المقترحة

جميع المسارات ضمن `/api/v1` وتتطلب JWT والتحقق من الدور والملكية:
- `POST /orders/shopping` — إنشاء طلب شراء وتوصيل.
- `GET /orders/:id/purchase-quote` — قراءة أحدث عرض شراء لصاحب الطلب والسائق المعيّن فقط.
- `GET /orders/:id/shopping-quotes` — العميل المالك يقرأ عروض الشراء.
- `POST /orders/:id/shopping-quote` — السائق المعيّن يرسل عرض تكلفة الشراء.
- `POST /orders/:id/shopping-quotes/:quoteId/approve` — العميل يوافق على عرض محدد، مع خيار صريح لتجاوز الميزانية.
- `POST /orders/:id/shopping-quotes/:quoteId/reject` — العميل يرفض عرضاً بانتظار الموافقة.
- `POST /orders/:id/purchase-proof` — السائق يسجل مرجع الفاتورة وملاحظة إثبات الشراء ورابط HTTPS اختياري.

لا يكفي إخفاء الأزرار في Flutter؛ يجب فرض كل شرط داخل Backend. لا يسمح بانتقال حالة السائق إلى `PICKED_UP` أو `DELIVERED` لطلب الشراء ما لم يكن هناك عرض شراء معتمد وإثبات شراء مسجل وفق سياسة المنتج.

## 6. الأمان والمال

- قيمة الشراء وأجرة التوصيل حقول/بنود منفصلة، ولا تُجمع أو تُستبدل ضمنياً.
- لا يُقبل سعر مولّد بواسطة AI. النموذج يستخرج الوصف فقط؛ السعر يقدمه السائق ويوافق عليه العميل.
- الميزانية حد معلن؛ أي تجاوز يحتاج موافقة صريحة جديدة.
- الموافقة مرتبطة بمعرف عرض ثابت ومبلغ وعملة وبصمة/نسخة العرض، لمنع اعتماد سعر تم تغييره لاحقاً.
- قفل صف الطلب ومعالجة التزامن وidempotency تمنع قبول عرضين أو إنشاء عمليات مكررة.
- تحقق من السائق المعتمد والمعيّن، والعميل المالك، والمدينة، وحالة الطلب في كل endpoint.
- لا تخزين لمفاتيح أو رموز أو بيانات دفع حساسة في التطبيق أو السجلات.
- فرض قائمة فئات مسموحة، ومنع السلع المحظورة أو المقيدة قانونياً أو عالية الخطورة، مع قواعد محلية قبل الإطلاق.
- لا يتم الشراء تلقائياً من خلال التطبيق ولا تُخصم أموال دون مزود دفع معتمد وسياسة واضحة.

## 7. اختبارات القبول

- إنشاء الطلب والتحقق من المدينة والعنوان والميزانية.
- عزل البيانات بين العملاء والسائقين.
- رفض عرض شراء من سائق غير معيّن أو غير معتمد.
- لا انتقال إلى الشراء/الاستلام دون موافقة العميل.
- تغيير السعر بعد الموافقة يبطل الموافقة السابقة.
- منع تجاوز الميزانية دون موافقة جديدة.
- رفض إثبات الشراء قبل الموافقة.
- منع تكرار الطلبات والعروض والموافقات تحت التزامن.
- استمرار تدفق المتاجر والطلبات المستقلة الحالية دون أي تغيير.
- اختبارات RTL/LTR واللغات الثلاث والوضعين الفاتح والداكن وتقليل الحركة.
- Flutter analyze/test، Backend build/test، ثم CI وبناء APK تجريبي بعد الدمج المصرح به.
